# 双侧有序队列与异构批量优化：设计与实验思路



## 1. 对题目的理解和联想

刚拿到题目时，我的第一感觉是规则很多很具体：A、B 两侧排序方向相反，同一个 key 内还要保持 FIFO；INSERT 不只是入队，还可能连续处理另一侧的多个 item；另外还要输出 Resolution、StateSummary、Snapshot 和 SnapshotMetrics。

一开始我想到的是生产者—消费者模型，但继续看会发现不太一样：两侧都保存 item，新 item 到来时会先尝试和另一侧处理，剩余部分才进入自己的队列。

后来我用“双侧有序队列、同 key FIFO、两侧按条件处理”这些关键词去查，也看了些常见模型，发现它很像量化交易里的订单簿：

- A、B 可以类比买卖双方；
- `key` 可以类比价格，`amount` 可以类比数量；
- 每个 key 是一档，同一档里按先来后到处理；
- 新 item 到来后，先从对面最优的一档开始处理；
- `Resolution` 可以看成一次双方实际处理的记录。

这个类比让复杂的规则更容易理解，但背景只用于辅助理解，具体行为仍以任务书为准。

整个任务链路

```text
读取事件
-> 校验 INSERT / REMOVE
-> 修改双侧队列并记录 Resolution
-> 每个事件后输出 StateSummary
-> 每隔 M 个事件保存 Snapshot
-> 对一批 Snapshot 计算 SnapshotMetrics
```

## 2. 阶段一：先做一个可靠的 CPU 版本

阶段一的目标是先完成可靠的 CPU 版本，并将它作为后续 CUDA 版本的正确性和性能基线。

阶段一的逐文件代码导读、容器选择、迭代器失效规则、复杂度、C++ 语法和高频追问，单独整理在 [`CPU阶段拷打准备.md`](CPU阶段拷打准备.md)。本节只保留设计概览。

### 2.1 数据结构

比较核心的结构有：

| 需求 | 实现 |
| --- | --- |
| A 按 key 从大到小、B 从小到大 | 两个排序方向不同的 `map` |
| 同一个 key 内保持 FIFO | 每一档使用 `list` |
| REMOVE 能根据 item_id 快速定位 | `unordered_map` 保存位置和迭代器 |
| 成功使用过的 item_id 不能复用 | `unordered_set` 保存历史 ID |

FIFO：`queue` 不能按 item_id 删除队中元素；`vector` 中间删除为 O(n)，还会移动元素并使位置索引失效。`list` 可以尾插、头取，并在已知迭代器时 O(1) 删除任意节点，所以用 `list`；

REMOVE 能根据 item_id 快速定位：一开始没考虑用哈希表做`item_id -> side + key + list迭代器`的映射，因为item_id唯一可以遍历查出来，但是后续发现效率太差了如果每个都查，所以优化加入哈希表；

成功使用过的 item_id 不能复用：用集合一是天生不重复，二是可以快查有无某个元素。

> map的排序？
>
> map默认是按key从小到大排的，传greater就是大至小，这样begin取的就是A的max_key，B的min_key

### 2.2 输出和 SnapshotMetrics

- `Resolution`：记录一次 current item 和 resident item 实际处理了多少。
- `StateSummary`：每个事件结束后，记录两侧最前面的档位和当前活跃 item 数。
- `Snapshot`：每隔 M 个事件保存一次完整的A B档位状态。
- `SnapshotMetrics`：只读取快照，从两侧各取前 K 档，直接计算 amount、`key_gap`、`balance_num/den` 和 `weighted_key_num/den`。

`SnapshotMetrics` 里的 K 指“每侧最多取前 K 个 level”，不是前 K 个 item。例如同一个 key 下有多个 item，它们在快照中已经合并成一个 level，只占 K 中的一个位置。有点像量化系统中有时只关注这个价位的能吞吐的总量不在乎实际上具体有几单。

### 2.3 阶段一功能性和边界测试

测试顺序是：题目示例 -> 流程边界 -> 学长提供的公开数据。

1. 先跑题目自带示例，确认基本流程和输出格式；
2. 再把重复 ID、非法参数、部分处理、连续跨档、REMOVE 队首/队中/队尾、空侧等情况拆开测试；
3. 最后使用公开数据和标准答案做完整回归。

前期还没有公开测试数据时，先用脚本根据任务规则生成输入；拿到公开数据后，再用其中的功能、边界和标准答案做完整回归。现有测试均通过，因此该 CPU 版本可以作为 CUDA 版本的 reference。


## 3. 阶段二：选择并实现 GPU 批量计算

### 3.1 为什么选择批量计算 `SnapshotMetrics`

阶段二选择的 GPU 目标是：**对大量相互独立的 `Snapshot` 批量计算 `SnapshotMetrics`**。

事件重放不适合直接拆成大量并行任务。第 `i+1` 个事件必须看到第 `i` 个事件处理后的队列，`INSERT` 还可能连续修改多个 level，因此事件之间存在严格的先后依赖。不同 Snapshot 之间没有这种依赖：一份 Snapshot 的结果只由自己的 A/B level 和运行时参数 `K` 决定，不会读取或修改其他 Snapshot。

所以并行单位定义为：

```text
输入工作单元：一份 Snapshot
输出工作单元：一份 SnapshotMetrics
工作单元之间：相互独立
输出顺序：与输入 Snapshot 顺序一致
```

CPU 版本继续作为 reference。CUDA 版本改变的是执行方式和数据布局，指标公式没有变化。

### 3.2 第一版正确 CUDA 实现

第一版采用最直接的对应关系：**一个 CUDA 线程处理一份 Snapshot**。每个 block 使用 256 个线程，线程用全局编号找到 Snapshot，然后顺序累加两侧前 `K` 档的 amount，最后写出一份结果。

```text
thread i
-> 读取第 i 份 descriptor
-> 累加 A 侧前 a_count 档
-> 累加 B 侧前 b_count 档
-> 写出 a/b amount、key_gap、balance_num/den、weighted_key_num/den
```

这一版的优点是逻辑简单，容易和 CPU 结果逐字段对照，因此保留为 `thread` 基线。它的问题是深 Snapshot 仍由一个线程串行累加，大量并行能力没有用于单份 Snapshot 内部。

### 3.3 当前 Host 到 Device 的输入布局

Snapshot 的深度可变，不适合用固定宽度二维数组。当前版本使用“描述符 + 连续 amount 数组”的扁平布局。

```cpp
struct CudaSnapshotDescriptor {
    std::uint64_t event_seq;
    std::uint64_t a_offset;
    std::uint64_t b_offset;
    std::uint32_t a_count;
    std::uint32_t b_count;
    std::int64_t a_extreme_key;
    std::int64_t b_extreme_key;
};
```

例如两份 Snapshot 经过整理后可以表示为：

```text
amounts = [A0 的 amounts..., B0 的 amounts..., A1 的 amounts..., B1 的 amounts...]

descriptor[0] = A0/B0 在 amounts 中的 offset 和 count
descriptor[1] = A1/B1 在 amounts 中的 offset 和 count
```

当前布局有四个要点：

1. A、B 共用一块连续 `amounts`，各自用 offset 和 count 定位，因此每批输入只需复制 descriptor 和 amounts 两块数据；
2. 只保存每侧前 `min(K, depth)` 个 amount，K 之后的 level 仍会被 parser 读取和校验，但不会上传到 GPU；
3. 只上传计算实际需要的 extreme key，不上传其余 level 的 key；
4. Host 输入使用 `cudaMallocHost` 分配的 pinned memory，并在多个 batch 之间复用容量。

这套布局把变长 Snapshot 转换成 GPU 容易连续读取的数组，也避免为了对齐而给浅 Snapshot 填充大量无效空间。

### 3.4 从单线程发展为多档协作 kernel

为了让深 Snapshot 也能使用更多线程，当前 CUDA 代码提供五种模式：

| 模式 | 每份 Snapshot 使用的线程数 | 作用 |
| --- | ---: | --- |
| `thread` | 1 | 第一版正确基线 |
| `group4` | 4 | 浅快照 |
| `group8` | 8 | 中浅快照 |
| `group16` | 16 | 中深快照 |
| `warp` | 32 | 深快照 |

协作 kernel 中，同一线程组按步长读取同一份 Snapshot：

```text
lane 0 读取 0、GroupSize、2*GroupSize ...
lane 1 读取 1、GroupSize+1 ...
...
```
一个线程组共同负责一份 Snapshot，每个线程只累加其中一部分 level，最后把各自的小计合并。
各线程先得到局部 A/B 和，再通过 `__shfl_down_sync` 在寄存器之间做归约，最后由组内第 0 个线程写结果。线程组大小是模板参数，因此 4、8、16、32 共用一套逻辑，编译时仍能生成固定大小的 kernel。

举例：
```
A 侧 10 档：A0 A1 A2 A3 A4 A5 A6 A7 A8 A9
B 侧  6 档：B0 B1 B2 B3 B4 B5
```
4 个线程的组内编号为 lane=0、1、2、3。它们这样分工：

| 线程 | 负责的 A 档 | 负责的 B 档 |
| --- | --- | --- |
| lane 0 | A0、A4、A8 | B0、B4 |
| lane 1 | A1、A5、A9 | B1、B5 |
| lane 2 | A2、A6 | B2 |
| lane 3 | A3、A7 | B3 |

### 3.5 自动选择线程档位

线程增加以后，一方面每个线程的循环次数减少；另一方面，一份 Snapshot 会占用更多线程，同一时刻能够处理的 Snapshot 数就会下降。所以临界点，也就是什么工作深度用什么线程档位最好，需要通过实验测定。


#### 3.5.1 用什么量表示一份 Snapshot 的工作深度

对一份 Snapshot，真正进入求和循环的是两侧各自前 `K` 档：

```text
a_count = min(K, A侧实际深度)
b_count = min(K, B侧实际深度)
work    = a_count + b_count
```

#### 3.5.2 怎样隔离并测量不同 kernel

实验的核心做法就是：**先构造 A、B 两侧 level 数相同的快照，再逐步增加两侧深度，观察每个工作深度下哪一个线程档位最快。**

例如：

```text
A 侧 16 档，B 侧 16 档  -> work = 32
A 侧 32 档，B 侧 32 档  -> work = 64
A 侧 64 档，B 侧 64 档  -> work = 128
……
```

每个深度单独构成一个 batch，同一 batch 中的 Snapshot 形状相同。然后保持输入不变，依次强制运行：

```text
thread、group4、group8、group16、warp
```

这样就能得到“同一批数据使用哪个档位最快”。随后不断增加深度，就能观察最快档位从 group4 切换到 group8、group16 和 warp 的位置。

为了避免结论只适用于某一种批量大小，同一个深度还会分别测试 `1、4、32、256、4096、65536` 份 Snapshot。单侧深度覆盖 `1～16384`，并在可能发生档位切换的位置增加更多测试点。

这里测量的只有 kernel 计算时间，不把文本解析、H2D 和 D2H 算进去。

#### 3.5.3 先做 thread/warp 二选一，再扩展为五档

实验分成了两步。

第一步只比较两个极端：

```text
thread：1 个线程处理一份 Snapshot
warp：  32 个线程处理一份 Snapshot
```

目的是先判断“让多个线程共同处理一份 Snapshot”是否有价值。结果很清楚：浅快照使用完整 warp 会浪费线程；快照越来越深后，warp 可以把很长的累加循环分给 32 个线程，因此优势不断扩大。例如单份、单侧深度 1024 时，warp 约快 6.14 倍；单侧深度 16384 时约快 16.85 倍。

第二步发现 1 和 32 之间跨度太大，所以补上 4、8、16 三个中间档位。对每一个工作深度，都比较下面五种方式：

```text
1、4、8、16、32 个线程处理一份 Snapshot
```

然后把各个测试点的最快档位排在一起，寻找连续、稳定的切换区间。这里没有看到某个点 group8 比 group4 快一点就立即设置阈值，因为几微秒任务容易波动；只有当不同 Snapshot 数量、相邻深度和改变测试顺序后都出现相同趋势，才把它作为临界点依据。

代表性结果如下。`work` 是 A/B 两侧实际参与计算的总档数，表中的加速比是 thread 时间除以建议档时间：

| work | thread | 建议档 | kernel 加速比 |
| ---: | ---: | ---: | ---: |
| 8 | 48.578 us | group4 20.321 us | 2.39x |
| 80 | 15.164 us | group4 8.352 us | 1.82x |
| 256 | 28.588 us | group8 6.558 us | 4.36x |
| 384 | 42.257 us | group8 15.299 us | 2.76x |
| 512 | 54.621 us | group16 6.328 us | 8.63x |
| 1024 | 31.730 us | warp 6.527 us | 4.86x |
| 32768 | 946.893 us | warp 37.786 us | 25.06x |

`thread` 继续作为第一版基线和命令行对照，但没有进入正式自动档位。极小测试中 thread 与 group4 的差异常被约 6 us 的启动开销覆盖；当浅 Snapshot 数量足够多时，group4 的结果更好，因此自动模式从 group4 起步。

#### 3.5.4 三个临界点怎样确定

实验观察到的稳定切换区间为：

```text
group4  -> group8     work 96～112 之间
group8  -> group16    work 448～512 之间
group16 -> group32    work 768～1024 之间
```

单个测试点的赢家并不总是随深度单调变化。几微秒的短任务容易受启动和调度波动影响，较大的输入还会跨越缓存容量并逐渐转为显存带宽主导。因此没有追随每个测试点相差几个百分点的局部赢家，而是选择在不同 Snapshot 数量、相邻深度和反向顺序复测中都比较稳定的边界：

| 有效工作深度 | 自动模式 | 选择依据 |
| ---: | --- | --- |
| `0～96` | `group4` | 浅层大批量中稳定优于 thread，更宽线程组还没有持续收益 |
| `97～448` | `group8` | 在不同 Snapshot 数量下整体最稳 |
| `449～1023` | `group16` | `work=512、768` 附近比 group8 更稳，warp 尚未持续占优 |
| `>=1024` | `warp` | 从 1024 开始形成连续优势，深度继续增加后收益扩大 |

所以代码最终使用 `96、448、1024` 三个阈值。它们是当前 RTX 4050 Laptop GPU、CUDA 12.9、block size 256 环境下的实测结果。

#### 3.5.5 为什么还需要工作量加权深度

当前自动模式是**一个 batch 只选择一个线程档位**：先用该 batch 内的全部 Snapshot 算出一个代表性工作深度，再选择一次 `group4/group8/group16/warp`，随后这一批的所有 Snapshot 都由同一种 kernel 处理。进入下一个 batch 后会重新统计和选择，所以不同 batch 可以采用不同档位。

前面的阈值由形状相同的 batch 得到，但正式 batch 可能同时包含大量浅 Snapshot 和少量超深 Snapshot。此时需要用一个数代表整个 batch。直接计算普通平均值：

```text
average_work = sum(work_i) / snapshot_count
```

会让数量多的浅 Snapshot 占主导。例如每 32 份中有 31 份 `work=64`、1 份 `work=8192`：

```text
average_work = (31*64 + 8192) / 32 = 318
```

它会选择 `group8`，但绝大多数 level 访问来自那份超深 Snapshot。实测中，group8 比该组最快的 warp 慢 2.70～3.24 倍。

因此正式 `auto` 改用：

```text
weighted_work = sum(work_i * work_i) / sum(work_i)
```

同一个例子中：

```text
weighted_work = (31*64^2 + 8192^2) / (31*64 + 8192)
              = 6607.30
```

于是选择 warp，与实测最快档一致。这个公式可以理解为：随机抽取一次 level 访问，观察它所在 Snapshot 的 `work`，所得期望值。深 Snapshot 贡献的访问更多，所以获得更高权重。

这个公式不只测试了“每 32 份中有 1 份超深”这一种输入。混合实验还包括 10% 深快照、`64/256/1024` 三档循环、浅深交替、浅深集中排列和 `96/112` 临界点混合。对完整 mixed 矩阵独立复测三轮后：

| 混合方式 | 加权公式改变档位后的结果 |
| --- | --- |
| 每 32 份中 1 份超深 | 6/6 次更快，加速 `2.04～3.24x` |
| 10% 为深快照 | 6/6 次更快，加速 `1.29～2.53x` |
| `64/256/1024` 三档循环 | 5/6 次更快；1 次慢约 5.5% |
| 浅深交替、集中排列、`96/112` 混合 | 两种公式选到同一档，共 21 次性能不变 |

合计来看，在加权公式实际改变档位的 18 次比较中，17 次更快、1 次更慢；另有 21 次选择没有改变。因此它不只对一个特例有效，尤其适合“少量深快照贡献了大部分 level 访问”的输入。不过它仍是当前硬件和测试数据上得到的经验规则，不能保证所有混合分布都更快。

#### 3.5.6 A/B 不对称和分桶为什么没有改变规则

补测固定总 `work`、A:B 分别为 `1:1`、`3:1` 和 `1:0` 的输入后，没有发现一套稳定的新边界。曾尝试用：

```text
2 * max(a_count, b_count)
```

这个修正的想法是：如果大部分 level 都集中在一侧，就把它看成更深的任务，更早选择较大的线程组。但实验结果有时变快、有时反而变慢。例如 4096 份单侧 `work=512` 的快照，原规则选择 group16，已经只比最快档慢约 0.08%；修正后会选择 warp，反而慢约 5.0%。

为了确认结果，又把 81 个不对称测试点完整测了三轮。只有 30 个点三轮都选出同一个最快档，说明很多档位的时间非常接近，容易因运行波动而交换名次；另外在很多不对称测试中，经常有“更深却由更小线程组选中”的现象。

重复实验排除偶然后，推测可能是因为：显存带宽等因素的限制，如果 group8 已经能够让显存带宽接近饱和，那么再增加线程不会让内存读取变快，反而减少了同时进行的独立 Snapshot 数量。

因此不为 A/B 不对称单独修改阈值。正式模式仍使用：

```text
work = a_count + b_count
```

还尝试过按三个阈值把一个混合 batch 拆成最多四组，分别启动 kernel。两种方案的成本关系是：

| 方案 | 好处 | 需要承担的开销 |
| --- | --- | --- |
| 整批使用一个档位 | 只启动一次 kernel，完整 batch 更容易填满 GPU | 一部分深浅 Snapshot 使用的档位不是各自最优 |
| 分成最多四个桶 | 每个桶可以使用更适合自身深度的档位 | 分类和维护桶；最多启动四次 kernel；每个桶变小后 GPU 利用率下降 |

为了尽量有利于分桶，下面的分桶耗时只累计各桶 kernel 的中位时间，不包含正式接入时还需要的分类、重排和恢复输出顺序。实测把“同组中最快的统一单 kernel”记为 `1.00x`：

| 混合 Snapshot 数 | 最佳统一单 kernel | 分桶耗时 | 实验结论 |
| ---: | ---: | ---: | --- |
| 256 | 1.00x | `1.46～3.25x` | 多次启动和小桶开销明显更大 |
| 4096 | 1.00x | 多数为 `1.12～1.71x` | batch 变大后差距缩小，但分桶多数仍慢 |

这说明在当前输入规模下，即使暂时不计算分类成本，分桶省下的“档位不匹配”时间仍小于多次 kernel 启动和小批次利用率损失。分桶并非在所有硬件和规模下都必然更慢；如果以后每个桶都足够大，结果可能改变。当前正式路径因此只为整个 batch 选择一个档位。

当前规则解决了少量深 Snapshot 被普通平均值掩盖的主要问题，但不能保证所有混合排列都选到理论上的最快档。它是在现有确定性实验中，性能、稳定性和调度复杂度之间的折中。

### 3.6 当前一批数据的完整执行流程

```text
读取并校验 Snapshot 文本
-> 直接写入 pinned descriptor 和统一 amounts
-> 根据本批 sum(work^2) 选择 kernel 档位
-> 扩容或复用 Device workspace
-> 两次 H2D：descriptor、amounts
-> 启动所选 kernel
-> D2H 复制 SnapshotMetrics
-> 按输入顺序写出 CSV
-> 清空逻辑长度并复用 buffer，继续下一批
```

批次大小既可以显式指定，也可以省略。省略时按 256 MiB 最坏输入预算计算，并限制为最多 262,144 份，这个参数也是根据实验中测量的传输带宽设置的，能充分利用带宽同时减少分批：

```text
max_bytes_per_snapshot = sizeof(descriptor) + 2 * K * sizeof(int64)
batch_size = min(262144, floor(256 MiB / max_bytes_per_snapshot))
```

这样 `K` 小时可以一次传更多 Snapshot，`K` 很大时又不会让单批内存无限增长。

正确性验证分两层：正式测试逐字段比较 CPU/CUDA 输出；大规模 benchmark 还比较固定 checksum。只比较总和可能让不同位置的错误互相抵消，所以逐字段结果才是主要正确性依据。

## 4. 阶段三：根据 profiling 持续优化

### 4.1 实验方法

公开 performance 数据总共只有 1348 份 Snapshot，适合做格式、边界和标准答案回归，但规模不足以稳定测量 GPU 吞吐。因此性能实验使用固定种子 `20260927` 生成的 50 万、100 万和 200 万份 Snapshot 数据，主要配置为名义单侧深度 50、`K=50`。

实验环境为 NVIDIA GeForce RTX 4050 Laptop GPU、CUDA 12.9、Windows、Release 构建，kernel block size 为 256。每次优化遵循同一流程：

1. 固定输入和参数；
2. 先验证 CPU/CUDA 全部字段一致；
3. 预热后重复运行，多组实验取中位数；
4. 同时记录 CPU、完整 CUDA、H2D、kernel 和 D2H；
5. 改变测试顺序复测，避免把频率和温度波动误认为代码收益。

完整原始记录和复现命令保存在 [`EXPERIMENTS.md`](EXPERIMENTS.md)，本节只保留影响最终设计的结论。

### 4.2 第一版为什么慢

50 万数据的第一版结果为：

| 项目 | 时间 |
| --- | ---: |
| CPU reference | 93.734 ms/pass |
| 第一版 CUDA | 369.473 ms/pass |
| CUDA 相对 CPU | 0.254x |

拆分 CUDA 时间后发现：

| 环节 | 时间 | CUDA 占比 |
| --- | ---: | ---: |
| Host 二次展平 | 278.462 ms | 75.4% |
| H2D | 48.574 ms | 13.1% |
| Host 临时输入释放 | 17.665 ms | 4.8% |
| kernel | 5.287 ms | 1.4% |

因此第一瓶颈不是计算公式，也不是 kernel，而是 Host 为 GPU 重新组织数据。这个结果决定了后续先优化数据路径，再优化 kernel。

### 4.3 最终采用的优化

#### 4.3.1 上次已经完成的优化

上次主要优化的是 Host 数据准备和内存管理。当时 kernel 仍采用一线程处理一份 Snapshot，重点是先消除调用 GPU 之前的额外开销。

| 优化 | 解决的问题 | 实验结果或判断 |
| --- | --- | --- |
| 准确 `reserve` | vector 反复扩容和复制 | 50 万 CUDA 从约 369.5 ms 降到 205.1 ms |
| 解析时直接生成 CUDA 布局 | 先构造嵌套 Snapshot、再二次 flatten | 降到约 75.8 ms，是前期收益最大的一步 |
| 复用 Device workspace | 每批重复 `cudaMalloc/cudaFree` | 降到约 65.2 ms |
| 可复用 pinned Host buffer | pageable memory 需要额外 staging | 当轮 H2D 降约 32.2%，CUDA 降约 25.1% |

这几步把主要瓶颈从 Host 二次整理和内存分配，逐渐转移到了 H2D 与 kernel 本身。加入 pinned buffer 后，50 万数据的 CUDA 时间约为 48.8 ms，相比第一版的 369.5 ms 已明显下降。

#### 4.3.2 本轮新增加的优化

本轮继续优化传输次数、batch 大小和 kernel 内部并行方式。

| 优化 | 解决的问题 | 实验结果或判断 |
| --- | --- | --- |
| A/B 共用 amounts | descriptor、A、B 三次 H2D | 改为 descriptor + amounts 两次 H2D；收益小但实现更简单 |
| batch 上限增至 262,144 | 小 batch 的传输与启动次数过多 | 50 万测试中 CUDA 比 65,536 batch 快约 9.1% |
| `group4/8/16/32` 自动分档 | 一线程处理深 Snapshot 时串行累加过长 | 最终 50 万数据 kernel 相对 thread 缩短 53.9% |
| 工作量加权深度 | 少量深 Snapshot 被普通平均值掩盖 | 稀疏超深和 10% 深快照测试均选到最快档 |

输入布局实验显示，当传输量足够大时，H2D 已稳定在约 11.5～12.0 GiB/s，说明此时主要受 Host 到 GPU 传输链路的带宽限制，而不是 `cudaMemcpy` 调用次数。把 descriptor 和 amounts 进一步塞进一个 byte arena，传输的总字节数没有减少，只少了一次 API 调用，没有稳定变快。因此最终停在两次 H2D。

#### 4.3.3 最终性能对比

使用同一份固定种子数据（50 万份 Snapshot、名义单侧深度 50、`K=50`），三个阶段的代表性结果如下：

| 阶段 | 主要实现 | CUDA 总时间 | kernel 时间 | 相对第一版 |
| --- | --- | ---: | ---: | ---: |
| 第一版 | 嵌套 Snapshot 二次展平，thread kernel | 369.473 ms | 5.287 ms | 1.00x |
| 上次优化后 | 直接生成连续布局、复用 Device buffer、pinned Host buffer | 48.789 ms | 5.189 ms | 7.57x |
| 本轮最终版 | two-copy、batch 262,144、多档 auto kernel、加权选档 | 45.310 ms | 2.437 ms | 8.15x |

从第一版到上次优化后，CUDA 总时间大幅下降，但 kernel 基本没有变化，说明主要收益来自删除 Host 二次展平、复用内存和加快 H2D。本轮把 kernel 从约 5.19 ms 进一步降到 2.44 ms；由于此时完整路径主要受 H2D 和其他固定开销限制，kernel 减半没有等比例反映到 CUDA 总时间中。

在最终版同轮配对实验中，CPU 字段中位数为 138.093 ms，CUDA 字段中位数为 45.310 ms，两者相除约为 3.05x；直接对每轮 CPU/CUDA 加速比取中位数则为 3.083x。两种写法略有差异，是因为“分别取时间中位数后相除”和“先计算每轮比值再取中位数”不是同一种统计方式。

上表用于展示优化阶段的代表性变化。各阶段并非在同一次进程中交叉运行，因此精确性能结论仍以第 5.2 节的最终配对实验为准。

### 4.4 做过但没有接入正式路径的方案

#### GPU 直接解析原始文本

正式版本仍然由 CPU 读取、解析和校验文本，再把 GPU 真正需要的数据整理成连续数组：

```text
Snapshot 文本
-> CPU 解析和校验
-> descriptor + amounts
-> H2D
-> GPU 计算指标
```

实验版本尝试少做这一步 CPU 解析，直接把原始 ASCII 文本送到 GPU：

```text
Snapshot 文本
-> H2D
-> GPU 解析十进制字符并计算指标
```

这个方案能够算出正确结果，但当前原型更慢。65,536 份、每侧深度 50 的测试结果为：

| 路径 | 输入大小 | H2D | kernel | D2H | CUDA 段总时间 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 连续布局 | 53.00 MiB | 4.338 ms | 0.395 ms | 0.594 ms | 6.692 ms |
| GPU 解析 ASCII 文本 | 74.26 MiB | 6.070 ms | 5.322 ms | 0.544 ms | 11.947 ms |

当前原型慢的原因很直接：ASCII 文本比连续数组大约多 40%，所以 H2D 要搬更多数据；GPU 还要逐字符识别数字、空格和换行，使 kernel 从 0.395 ms 增加到 5.322 ms。最终 GPU 解析文本的 CUDA 段耗时约为连续布局的 1.79 倍。

因此当前结论是：**现阶段由 CPU 解析文本，再把紧凑数组传给 GPU 更合适。** 这不代表 GPU 解析文本永远更慢。正式命令的大量时间仍花在文本解析、完整校验和 CSV 格式化上；如果以后实现了换行定位、整数解析和完整校验都在 GPU 上完成的等价版本，还需要重新做端到端比较。当前实验没有完成这些正式校验，所以只保留为 benchmark。

#### H2D 与 kernel overlap

正常路径按顺序处理每一批：

```text
第 1 批：H2D -> kernel -> D2H
第 2 批：H2D -> kernel -> D2H
```

overlap 实验使用两条 stream 和两套 buffer，希望在第 1 批计算时同时上传第 2 批：

```text
第 1 批：       kernel
第 2 批：H2D
              两者尽量重叠
```

如果传输和计算使用的硬件资源互不冲突，重叠部分就可以被隐藏。但本机实测中，50 万数据连续提交 20 次时：

```text
各阶段时间相加：                         35.185 ms/pass
从流水线开始到全部结束的实际耗时（墙钟）：35.128 ms/pass
被并发执行隐藏的时间：                    0.057 ms/pass
```

只隐藏了约 0.16%，100 万和 200 万测试也没有得到稳定收益。

本机只有一个异步拷贝引擎。设备虽然允许传输与计算并发，但 H2D 要向显存写数据，kernel 又要从显存大量读取 amount，两者并发时会竞争内存相关资源。结果是时间看起来重叠了，各阶段本身却可能变慢，收益基本被抵消。因此 overlap 代码只保留为实验入口，正式路径仍按 `H2D -> kernel -> D2H` 顺序执行。

#### 其他未采用方案

| 尝试 | 原本想解决什么 | 为什么没有采用 |
| --- | --- | --- |
| 用 `2*max(A,B)` 修正工作深度 | 单侧特别深时提前选择更大的线程组 | 有些点变快、有些点反而选到过宽档位，没有稳定收益 |
| 按深度把一个 batch 分桶 | 让浅、深 Snapshot 分别使用最合适的 kernel | 要启动多个小 kernel，小桶不容易填满 GPU，实测多数更慢 |
| descriptor 和 amounts 合成一次 H2D | 再减少一次 `cudaMemcpy` 调用 | 总传输字节数没有减少，带宽已经达到平台，没有稳定变快 |


这些方案并不是无法运行，而是当前实验中收益不稳定，或者增加的复杂度超过了节省的时间，因此没有替换正式路径。

## 5. 最终结果

### 5.1 第一版与最终版

在同一类 50 万、名义单侧深度 50、`K=50` 数据上：

| 版本 | CUDA 时间 | 相对第一版 |
| --- | ---: | ---: |
| 第一版：嵌套输入、二次展平、thread kernel | 369.473 ms/pass | 1.00x |
| 最终版：直接布局、pinned、复用、two-copy、auto | 45.310 ms/pass | 约 8.15x |

这里的提升来自整条 CUDA 数据路径，不应全部归因于 kernel。前期最大收益来自删除 Host 二次展平，后期 kernel 分档主要缩短计算部分。

### 5.2 最终 prepared-data 配对结果

固定种子、名义单侧深度 50、`K=50`、batch 262,144。下表是三组交叉顺序实验的字段中位数：

| Snapshot 数 | 模式 | CPU | CUDA | H2D | kernel | D2H | 每轮 CPU/CUDA 中位数 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 500,000 | thread | 135.309 ms | 46.237 ms | 28.095 ms | 5.282 ms | 5.294 ms | 2.842x |
| 500,000 | auto | 138.093 ms | 45.310 ms | 28.088 ms | 2.437 ms | 5.407 ms | 3.083x |
| 1,000,000 | thread | 325.417 ms | 283.113 ms | 181.392 ms | 50.400 ms | 24.168 ms | 1.149x |
| 1,000,000 | auto | 313.272 ms | 279.366 ms | 188.875 ms | 46.140 ms | 24.540 ms | 1.057x |
| 2,000,000 | thread | 537.262 ms | 637.468 ms | 429.311 ms | 110.336 ms | 51.262 ms | 0.866x |
| 2,000,000 | auto | 508.523 ms | 620.501 ms | 420.413 ms | 105.503 ms | 50.254 ms | 0.805x |

三种规模的 CPU/CUDA 输出全部一致。auto 相对 thread 的 kernel 时间分别缩短 53.9%、8.5% 和 4.4%，完整 CUDA 时间分别缩短 2.0%、1.3% 和 2.7%。

CPU 时间总体随 Snapshot 数增加而增长，但受运行状态影响并非严格的二倍关系。CUDA 在这三点上更不是稳定线性增长：规模变大后 H2D 的占比和波动明显上升，200 万时 H2D 约占完整 CUDA 时间的 67.8%。所以当前实验不能得出“数据越大，GPU 加速越高”的结论；在 200 万规模上，CUDA 反而比 CPU 慢。

三组数据实际上传的字节数基本按规模翻倍，但有效 H2D 带宽没有保持不变：

| Snapshot 数 | 估算输入量 | H2D | 有效 H2D 带宽 |
| ---: | ---: | ---: | ---: |
| 500,000 | 341.44 MiB | 28.088 ms | 11.87 GiB/s |
| 1,000,000 | 682.99 MiB | 188.875 ms | 3.53 GiB/s |
| 2,000,000 | 1365.68 MiB | 420.413 ms | 3.17 GiB/s |

如果运行时带宽和每批固定开销保持不变，H2D 应当近似随输入字节数线性增长。这里的非线性主要来自有效传输带宽下降。当前实验没有在运行过程中同步记录 PCIe 链路状态、GPU/显存频率、功耗和温度，因此不能把下降唯一归因于某个原因；可能因素包括笔记本动态功耗与温度、Windows/WDDM 调度、PCIe 状态以及 Host 内存系统波动。这个现象属于当前测试环境下的运行时瓶颈，不表示 H2D 的理论复杂度超过线性。


## 6. 当前结论与限制

目前已经完成任务书要求的 CPU reference、第一版正确 CUDA、持续 profiling、最终优化版本和结果说明。最重要的结论有三点：

1. `SnapshotMetrics` 的确适合按 Snapshot 并行，但它的单份计算很轻，数据移动和输入输出容易盖过计算收益；
2. 最有效的优化不是增加复杂 kernel，而是让 parser 直接生成最终布局、复用内存并减少传输次数；
3. 多档 kernel 能稳定缩短 kernel 时间，但在大规模输入上，完整 CUDA 时间主要由 H2D 决定。

当前限制如下：

| 限制 | 影响 | 后续方向 |
| --- | --- | --- |
| 正式输入仍为文本，输出仍为 CSV | 端到端主要耗在解析、校验和格式化 | 让上游提供连续二进制数据，或实现校验等价的 GPU 融合解析 |
| 当前任务只有一次指标计算 | 输入上传后没有真实的第二次复用 | 出现多个 K 或更多统计时，再让数据常驻显存并融合多个 kernel |
| 本机只有一个异步拷贝引擎，计算与传输都受显存带宽影响 | 双 stream overlap 几乎没有收益 | 在计算更重的指标或不同硬件上复测 |
| 一个 batch 只选择一个线程档位 | 混合排列仍可能存在局部次优 | 收集更多真实分布后，再评估更低成本的调度特征 |
| 实验只覆盖 RTX 4050 Laptop GPU、CUDA 12.9 和 Windows | 临界点和加速比不能直接外推 | 在其他 GPU 和 Linux 环境复测并重新标定阈值 |

阶段三到这里可以形成完整闭环：保留 thread 基线，用逐段计时找到 Host 整理和 H2D 瓶颈，分别验证数据布局、内存复用、pinned memory、kernel 分档、batch、文本解析和 overlap，最后只把具有稳定收益且复杂度合理的方案接入正式路径。
